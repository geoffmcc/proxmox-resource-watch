# Security baseline and threat model

Baseline: `origin/main` at `431fd7df505338fdbe4c77d06c2e67cc1c77abb6` (fetched 2026-11-05). Branch before work: `main`; implementation branch: `security/production-hardening`.

## Architecture inventory

`install.sh` is the root installer. Python executables in `src/` are installed in `/usr/local/sbin`; configuration is `/etc/default/proxmox-resource-watch`; service and timer units are installed in `/etc/systemd/system`; state and dated JSONL/gzip records are kept in `/var/log/proxmox-resource-watch`; prior versions may leave legacy logs in `/var/log`; installer backups use `/var/backups/proxmox-resource-watch`. Eight supplied services run as root by default: sampler, report/scheduled/daily, alert, follow-up, guests, and Jellyfin helper. (Report has three entrypoint units.) Timers invoke oneshot services. Root currently permits complete `/proc` inspection, local `pvesh` GET, cgroup/container-root reads, private existing logs, and the configured root mail transport. No service controls guests. The existing units already use private temp, read-only system paths, no-new-privileges, memory/swap ceilings and deadlines for oneshots.

The sampler reads `/proc` and `/sys`, writes daily logs and retention files. Report/alert/follow-up read logs and write alert or delivery state. Guests runs a fixed `pvesh get /cluster/resources` command with bounded output and time, then writes guest snapshots. The Jellyfin helper reads an identified container's log through read-only proc/cgroup metadata and replaces a bounded snapshot. Report also runs bounded `journalctl`; mail uses fixed `mutt` or `sendmail` argument vectors; Discord uses a validated HTTPS webhook with proxies and redirects disabled. Configuration is a systemd EnvironmentFile and can hold a webhook credential. Process arguments, guest names, historical records, mail bodies, and report attachments can contain sensitive data; log directory and config must stay private.

## Threat model

A malicious repository contribution is high impact if an administrator executes its installer as root; reviewed immutable source and PR gates are the primary boundary. Compromised Actions dependencies can alter CI results or steal CI tokens; they have no production host access in this design. Malformed configuration can redirect paths, disable delivery, or fail units, although the validator rejects many unsafe values. A local actor able to modify root-owned installation destinations or source files can attempt symlink/race attacks; a truly root-owned private parent limits this on a normally configured host. Untrusted process names, guest metadata, journal/Jellyfin data and historical logs may contain control characters, malformed JSON, and oversized content; fixed subprocess arguments prevent shell injection, while limits and sanitization need regression coverage. Webhook compromise allows sending to that channel and requires rotation; exfiltration by redirects or proxies is explicitly blocked. Corrupted state can affect alert deduplication. Excessive data or stuck tools can disrupt monitoring, bounded by service and parser limits. Failed upgrades can leave mixed installed code, while history must remain intact. Production host or guest changes are outside this work.

## Baseline findings

| Severity | Finding and affected code | Exploitability prerequisites and impact | Evidence |
| --- | --- | --- | --- |
| HIGH | Installer replacement preflight is incomplete (`install.sh`: backup/install loops). | A preexisting symlink or special file at a script/unit destination, or a writable destination parent, can make a root upgrade unsafe or fail partway through. A local actor normally needs prior control of a privileged installation path; malformed preexisting installations also qualify. | `backup_if_exists` accepts arbitrary existing types; destination checks exist only for config and log directory, and occur after some writes. |
| MEDIUM | Installer can leave a mixed installation after failure (`install.sh`). | Disk, service, or notification failure during upgrade can leave scripts/units changed with earlier services running; operator recovery is required. | Sequential replacement precedes daemon reload and service tests; no automated rollback. |
| MEDIUM | Existing configuration is not validated before restart (`install.sh`). | Administrator error or tampering can cause a failed restart or unsafe optional path. | Validator exists but installer does not invoke it. |
| LOW | CI has no security analyzers or immutable action pins (`.github/workflows/tests.yml`). | Compromised action tags or security regressions can evade current checks. | Checkout/setup-python use moving major tags; only regression workflow exists. |
| INFORMATIONAL | Root services retain broad host visibility. | A code execution defect in a service has root impact; existing systemd limits reduce filesystem writes but do not constitute a privilege drop. | Units omit `User=`, while host inspection and local mail/Proxmox APIs rely on present root behavior. |

No confirmed shell injection was found in the reviewed subprocess calls. The practical attack surface is privileged file replacement, untrusted data parsing, credentials, and software distribution. New restrictions must be tested against actual Proxmox mail and `pvesh` behavior before changing service identity or syscall/network policies.
